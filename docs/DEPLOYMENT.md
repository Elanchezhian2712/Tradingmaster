# Deployment

## Local development

```bash
npm install                      # installs all workspaces
npm run dev                      # starts apps/web on http://localhost:5173

docker compose up -d postgres    # Postgres for the API (see port note below)
cd services/api
python -m venv .venv && .venv/Scripts/activate
pip install -r requirements.txt
cp .env.example .env             # adjust JWT_SECRET etc. for anything beyond local dev
alembic upgrade head
uvicorn app.main:app --reload
```

`docker-compose.yml` maps Postgres to host port **5433** (not 5432) and
Redis to **6380** (not 6379) — offset from the standard ports specifically
because a dev machine may already have its own Postgres/Redis running on
the defaults, and a silent connection to the wrong database is a much
worse failure mode than an unfamiliar port number. If nothing else is
using 5432/6379, feel free to change both `docker-compose.yml` and
`services/api/.env` back to the defaults.

## Full stack via Docker Compose

```bash
docker compose up -d --build
```

Brings up Postgres, Redis, and the FastAPI service (`services/api/Dockerfile`).
The frontend is not containerized yet — it's a static Vite build
(`npm run build -w apps/web` → `apps/web/dist/`) meant to be served by
any static host (Nginx, Cloudflare Pages, S3+CDN, ...) or added as its own
Compose service later; see `docs/FUTURE.md`.

## Environment variables

See `services/api/.env.example` for the full list with defaults. Never
commit a real `.env` — the repo's `.gitignore` already excludes it. At
minimum, set a real `JWT_SECRET` (`python -c "import secrets;
print(secrets.token_urlsafe(64))"`) before anything beyond local dev, and
set `CORS_ORIGINS` to the frontend's real deployed origin(s).

## Database migrations

```bash
cd services/api
alembic revision --autogenerate -m "describe the change"   # after editing app/models/*.py
alembic upgrade head
```

Always review an autogenerated migration before applying it — Alembic
diffs models against the live database and gets some things right by
convention (indexes, FKs) but doesn't know your intent for renames or data
backfills.

## Production hardening checklist (not yet done)

- Real TLS termination in front of the API (this repo assumes a reverse
  proxy or platform load balancer handles it — the app itself serves plain
  HTTP).
- A real secret manager (Vault, cloud provider secrets store, ...) instead
  of an `.env` file, for `JWT_SECRET` and the database password.
- Structured log shipping (the app already logs structured lines with a
  request id — `app/main.py`'s middleware — but nothing ships them
  anywhere yet).
- A refresh-token flow (`docs/FUTURE.md`) rather than a single long-lived
  access token.
- Horizontal scaling of the API is straightforward (it's stateless per
  request; sessions live in the JWT, not server memory) but hasn't been
  load-tested.
